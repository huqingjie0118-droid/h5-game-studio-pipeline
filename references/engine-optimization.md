# 游戏引擎与性能优化模块 (Engine & Performance Module)

> 本文件是 h5-game-studio-pipeline 的**程序性**引擎性能方法论，由 `engineering-lead` 在 Stage 4（集成）主路由，`art-director`（技术美术侧）配合。
> **分工边界**：`tech-art.md` 管"视觉层怎么做"（资产规格/渲染方案/VFX/预算），本文件管**"引擎层怎么跑"（循环/逻辑/内存/加载/帧率/性能流程）**。tech-art 管"画得省"，本文件管"跑得快、跑得稳、加载快"——一张图的两面。
> **与 Game Engine skill 的关系**：通用引擎知识（碰撞算法、WebGL/WebGPU、Phaser/Three.js 框架、Web Audio）去 `game-engine__skillhub` 查；本文件专注 **Canvas 2D 编排流水线的性能方法论**，两者不重复造轮子。
> 与 `design-principles.md`（§三 架构速记）、`pitfalls.md`（P21–P28 事故型坑）互补：**本文件管"怎么做对且可持续"，它们管"做到什么标准"和"别踩什么雷"。**

## 铁律：执行顺序不可逆

```
引擎架构基线（循环/固定步长/状态管理）→ 性能预算管理（总账先立）
   → 性能测量与 Profiling SOP（先量后改，禁止凭感觉）
   → 渲染性能优化 → 逻辑与物理性能优化
   → 内存管理 → 加载性能 → 帧率稳定性与移动端
   → 性能监控仪表盘 → 性能回归与基准
```

任何一条写不清，**不准进入下一条**。引擎性能的第一铁律是 **"先 profile 再优化"**（呼应 P24）——没有测量就优化 = 在给错误的地方加速。**性能是预算管理的产物，不是救火的结果。**

## §1 引擎架构基线（Architecture Baseline）

> 以下五条是 Canvas 2D 引擎的**默认地基**，任何项目从 Stage 4 第一天就按此搭建，不是"以后再说"。（从 design-principles §三 提炼为可执行模块）

### 1.1 游戏循环（固定步长 + 渲染插值）
```
INPUT（读输入）→ UPDATE（固定步长 50Hz, dt=1/50，累加器消费真实时间）→ RENDER（插值绘制）
```
- 逻辑固定步长保证可复现（联机/回放依赖，呼应 P21）；渲染随 rAF 尽量快，状态间插值平滑。
- **反例**：`"用每帧真实 dt 直接驱动物理"` = 帧率波动即物理/计时不一致，联机服务端对不上。

### 1.2 输入抽象层
- 输入抽象成**动作**而非原始按键（jump = Space / 手柄 A / 触摸），统一 Pointer Events（呼应 P14），封装 `toCanvasCoord()`（呼应 P13）。

### 1.3 状态管理
- 离散状态（Idle/Walk/Jump）用**状态机**起步；跨系统通信用**事件/观察者**（血量→UI）；上千同类实体才考虑 ECS——**默认从状态机起步，性能真不够再上 ECS**。

### 1.4 模块边界
- 渲染、逻辑、输入、网络、存档**分层解耦**；随机逻辑集中纯函数模块（呼应 P20）；战斗/经济纯函数可移植服务端（呼应 P29）。

### 1.5 反模式闸门（每个模块写码前自查）
| 别做 | 该做 |
|------|------|
| 每帧更新一切 | 事件/脏标记驱动（P24） |
| 热循环里 new 对象 | 对象池（P22） |
| 啥都不缓存 | 缓存引用（不在循环里查 DOM/属性） |
| 不 profile 就优化 | 先量再改（§3） |
| 输入混逻辑 | 抽象输入层 |

## §2 性能预算管理（Budget First）

> 🔴 **铁律**：性能预算在 Stage 4 **第一天**立项，写进 `docs/` 性能页，Gate 4 逐行核对。**没有预算表的优化 = 没有尺子的装修。**

### 2.1 总账（60FPS = 16.67ms）
| 系统 | 预算 | 占帧 | 说明 |
|------|------|------|------|
| 输入 | 1ms | 6% | 读输入、抽象分发 |
| 物理 | 3ms | 18% | 碰撞/移动 |
| AI | 2ms | 12% | 敌人决策 |
| 逻辑 | 4ms | 24% | 状态/事件/经济 |
| 渲染 | 5ms | 30% | 全部 drawImage（对应 tech-art §6） |
| 缓冲 | 1.67ms | 10% | GC 尖峰、浏览器开销 |

### 2.2 分账关系
- **本文件总账 ↔ tech-art §6 分账**：渲染的 5ms 由 tech-art 的"同屏 drawImage ≤300/源切换 ≤8/粒子 ≤200"兑现；逻辑的 4ms 由本文件 §5（池化/脏标记/碰撞优化）兑现。**两表合起来才是完整预算，Gate 4 两表都查。**

### 2.3 预算模板（Stage 4 立项时填，`[PLACEHOLDER]` 纪律同前）
```
| 系统 | 预算 | 实测（抓帧） | 状态 |

| 输入 | 1ms  | [PLACEHOLDER] | [未测/达标/超标] |
| 物理 | 3ms  | ... | ... |
| 渲染 | 5ms  | ... | ... |
```

## §3 性能测量与 Profiling SOP（先量后改）

> **三问法**：*快不快（帧率）→ 哪段慢（分段计时）→ 为什么慢（调用栈/计数）*。禁止跳过任何一问。

### 3.1 测量工具栈
| 层级 | 工具 | 用途 |
|------|------|------|
| 帧率 | 自建 FPS HUD（§9） | 持续观测，无需 DevTools |
| 分段 | DevTools Performance 抓 10s 主循环 | 定位 UPDATE/RENDER 占比 |
| 调用 | Performance 火焰图 | 具体函数耗时 |
| 内存 | DevTools Memory / heap snapshots | GC 尖峰、泄漏 |
| 计数 | 代码埋点（drawImage 次数/粒子数） | 对照预算表（tech-art §6） |

### 3.2 Profiling SOP（决策树）
```
帧率 < 目标？
├─ 偶发卡顿（尖峰） → Memory/GC 检查：对象池是否生效（P22）？每帧 new 了啥？
├─ 持续低帧
│   ├─ Performance 抓帧：UPDATE 占比高？
│   │   ├─ 物理/碰撞慢 → §5.3 空间哈希/宽阶段裁剪
│   │   ├─ AI 慢 → §5.4 分帧/降频
│   │   └─ 逻辑慢 → §5.2 脏标记/事件驱动
│   └─ RENDER 占比高？
│       ├─ drawImage 次数超预算 → §4.1 合批/§4.2 离屏缓存/§4.3 裁剪
│       ├─ source 切换多 → §4.1 图集（tech-art §3）
│       └─ filter/shadowBlur 出现 → 立即删除（tech-art §1 天价操作）
└─ 首屏慢（加载） → §7 渐进加载/预取
```

### 3.3 测量纪律
1. **在目标设备上测**：移动端真机 ≠ 桌面 DevTools；低端机 ≠ 开发机。
2. **在最坏场景测**：Boss 战同屏峰值、弹幕全开、粒子上限——**平均帧率是骗人的，P1（最差 1%）才致命**。
3. **每次优化后重测**：before/after 记录（帧率、P1、drawImage 计数、内存），进 §10 回归基准。

## §4 渲染性能优化（画得省）

> 与 tech-art §3/§6 互为表里：本文件管"引擎怎么组织绘制"，tech-art 管"资产怎么准备"。

### 4.1 drawImage 合批
- 同源图连续绘制：把同图集的对象分组绘制（按 atlas 源排序），减少状态切换（tech-art §3）。
- 少用缩放 drawImage：预生成缩放版本（tech-art §3.2），运行时 1:1。

### 4.2 离屏缓存（静态层）
- 静态背景/光照层/UI 底图预渲染到离屏 canvas，主循环整块 `drawImage`（呼应 P11）。
- **纪律**：只有"真在动的"进主循环；层序恒定（背景→光照→动态→UI）。

### 4.3 视口裁剪（Culling）
- 只绘制与视口相交的对象：`if (x + w < cam.x || x > cam.x + viewW) continue;`——**离屏对象不画**，这是同屏 drawImage 预算的最大来源节省。
- 网格索引：对象按屏幕网格登记，只遍历相邻网格（与碰撞共享网格，见 §5.3）。

### 4.4 纹理/状态保护
- 禁止每帧改 `globalAlpha`/`filter`/`shadowBlur`（tech-art §1 天价/很贵操作）。
- `save/restore` 成对，绘制完复位混合模式（呼应 P26）。

## §5 逻辑与物理性能优化（跑得快）

### 5.1 对象池（Object Pooling，呼应 P22）
- **适用**：高频 spawn/destroy——子弹、粒子、飘字、AoE 圈、掉落。
- **做法**：预分配固定数组，活跃/空闲两集合，复用实例仅切状态；**数量封顶**（移动 ≤ 粒子上限，见 tech-art §6）。
- **验收**：抓帧确认 GC 尖峰消失；`new` 计数从每帧 N 降到 0。

### 5.2 脏标记与事件驱动（呼应 P24）
- 状态变化才更新：血量变化才刷血条；位置变化才上报网络（呼应 P30 增量同步）。
- 事件总线：跨系统通信走事件，不轮询。

### 5.3 碰撞检测优化
| 规模 | 方案 |
|------|------|
| ≤50 实体 | 暴力 AABB 两两检测（够了就别优化） |
| 50–500 | **空间哈希/网格**：只检测相邻格子（与 §4.3 共享网格） |
| 弹幕密集 | 宽阶段（网格/四叉树）粗筛 + 窄阶段精确检测 |
- **反例**：`"100 个敌人 × 全量两两检测"` = 4950 次/帧，纯逻辑就爆预算——上空间哈希后降为 ~10 次/格。

### 5.4 AI 与高频逻辑分帧
- AI 决策按帧轮询分摊（每帧只更新 1/N 的敌人 AI，30Hz 即可感知不到）。
- 冷却/计时走游戏内累计时间（不每帧算 `Date.now()`）。
- 批量遍历用单循环合并，避免每实体多次遍历。

## §6 内存管理（别让内存背锅）

### 6.1 纹理内存总账
- 对接 tech-art §2：移动 ≤64MB / 桌面 ≤128MB；RGBA = 宽×高×4 字节，**生成前算总账**。
- 卸载场景/关卡时**释放 Image 引用**（`img.src = ''` + 置 null），防移动端显存累积闪退。

### 6.2 GC 控制
- 热循环零分配：不 `new`（用池）、不拼接字符串（飘字用模板复用）、不隐式分配（`arr.map` 每帧 = 垃圾）。
- 事件监听器及时解绑（面板关闭时，呼应 P01/P02）。

### 6.3 启动包体积预算
- 首屏 ≤2MB（核心资源），其余 lazy load（呼应 P28）。
- 体积审计：构建产物按类型统计（JS/PNG/音频），超预算的转 WebP/压缩/砍素材。

## §7 加载性能（快不快的另一半）

### 7.1 渐进加载策略
```
启动：核心 <2MB（主角/首场景/UI 骨架）→ onload 即交互
游戏内：玩法资源按需 lazy load（下一关预取）
失败：每个资源挂 onerror → PNG→SVG→Emoji 回退（P06）+ 超时兜底
```

### 7.2 预取与并发
- 预取策略：当前场景预取下一场景；UI 图集一次性预载（图标小、张数多，适合早载）。
- 并发上限：浏览器同域 ~6 连接，批量加载走队列管理，避免排队阻塞关键资源。

### 7.3 加载 UI
- 有进度条（真实进度，非假动画）；失败重试按钮；弱网降级（跳过非核心资源，可后补）。

## §8 帧率稳定性与移动端（稳比快重要）

### 8.1 dt 钳制与后台暂停（呼应 P23）
```
dt = min(dt, 0.05)          // 回前台瞬间防物理爆炸
visibilitychange → hidden 暂停主循环；回前台重置 last=now
计时走"游戏内累计时间"，不依赖墙钟
```

### 8.2 动态降级（保命开关）
- 帧时间连续 N 帧超预算 → 自动降档（dpr 2→1.5→1、粒子减半、关 overlay——对接 tech-art §9 降级档位）。
- **纪律**：降级纯视觉不改玩法判定（与 tech-art 分界契约一致）；恢复条件（帧时间回落）后回档。

### 8.3 目标帧率纪律
- 移动端默认 **30FPS 达标**（视觉 30 往往够），先保 30 再冲 60；桌面 60。
- 性能目标写进 GDD/性能页：`[PLACEHOLDER]` 设备清单（低端安卓机 ×1、iPhone 老款 ×1、桌面 Chrome ×1）。

## §9 性能监控仪表盘（性能 HUD）

> H5 游戏没有内置 profiler，**轻量 HUD 是持续观测的唯一手段**。开发期必开，发布期可关（保留开关）。

```javascript
// 最小实现：每 500ms 聚合一次，覆盖层显示
{
  fps: 当前帧率（EMA 平滑）,
  p1: 最差 1% 帧时间（滚动窗口）,
  drawCalls: 每帧 drawImage 计数（埋点累加）,
  particles: 活跃粒子数,
  texMB: 已加载纹理内存估算（assets 汇总）,
  gcStalls: 近 500ms 内 >16ms 的帧数（GC 尖峰指示）
}
```
- **纪律**：HUD 数据必须能对照 §2 预算表；埋点计数器用整数累加，不用数组 push（防 GC，呼应 §6.2）。

## §10 性能回归与基准（性能也要防回归）

> 与 design 各模块的 Playtest 失败信号同纪律：**没有基准的性能优化 = 下周就不知道这周优化了什么。**

### 10.1 基准场景（Benchmark Scenes）
| 场景 | 内容 | 度量 |
|------|------|------|
| 登录/主城 | 全 UI + 静态背景 | 首屏时间、FPS、内存 |
| Boss 战峰值 | 同屏最大实体数 + 全特效 | FPS、P1、drawImage 计数 |
| 弹幕全开 | 粒子上限 + additive 满层 | FPS、粒子数 |
| 后台切换 | 切后台→回前台 | 恢复帧率、无跳变 |

### 10.2 性能测试（Gate 4/5 自动/半自动）
- 基准脚本：加载基准场景 → 跑 30s → 采集 FPS/P1/内存 → 与上次基线对比。
- **回归闸门**：FPS 均值下降 >10% 或 P1 恶化 >20% → 阻断合并（quality-lead 出 `PERF_REGRESSION` 判定）。

### 10.3 记录纪律
- 每次性能改动记 before/after（帧率、P1、drawImage、内存、加载时间）——**进 `docs/PERFORMANCE.md`，不写进代码注释就丢**。
