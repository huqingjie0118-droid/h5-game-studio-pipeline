# 游戏系统与机制设计模块 (Systems & Mechanics Design Module)

> 本文件是 h5-game-studio-pipeline 的**程序性**游戏设计方法论，由 `design-strategist` 在 Stage 2（grill-me / GDD）主路由。
> 与 `design-principles.md`（质量准线：PASS 长什么样）和 `pitfalls.md`（事故型坑）互补：**本文件管"怎么做"，那两个管"做到什么标准"和"别踩什么雷"。**

---

## 铁律：执行顺序不可逆

```
Fun Hypothesis → Design Pillars → 三层核心循环 → 机制活检
   → 经济账本(Sources/Sinks) → 数值 Tuning 纪律 → Juice 规格
   → 系统交互矩阵 → Playtest 失败信号
```

任何一条写不清，**不准进入下一条**。写不清就不往下走——这是防"空中楼阁 GDD"的唯一栅栏。

---

## §1 Fun Hypothesis（一句话乐趣锚）

- **定义**：用一句话写完 **"这游戏好玩的核心是 ____"**。
- **时机**：grill-me 任何 Tier 提问之前先逼出这句话。写不出 = 概念没成型，回到 Tier 1 继续挖原始动词（战斗/移动/放置/收集），**禁止跳到系统或经济**。
- **反例 vs 正例**：
  - ✗ `"一个修仙放置游戏"` —— 这是品类，不是乐趣。
  - ✓ `"好玩的核心是——用最低操作成本看到数值滚雪球式的膨胀反馈"` —— idle 驱动，可推导决策。
  - ✓ `"好玩的核心是——五行相克带来的'猜中克制→一击逆转'的博弈快感"` —— 策略驱动。
- **校验**：这句话能推导出 ≥1 个**可测试的玩家决策**吗？不能 → 重写。

---

## §2 Design Pillars（不可妥协的体验标准）

- **定义**：从 Fun Hypothesis 推 **3–5 条"玩家必须感受到的体验"**，之后每个机制 / 数值用这几条过审。
- **提取纪律**：每条 pillar 必须是**可证伪的体验陈述**，不是功能列表。
  - ✓ `"每次击杀都该有'我变强了'的可见反馈"`（可测）
  - ✗ `"丰富的装备系统"`（不可测，是功能不是体验）
- **过滤器规则**：新增任何系统前问 *"它服务哪条 pillar？"* 服务不到 → 砍或重做。两条 pillar 冲突时，由 Fun Hypothesis 裁决。
- **范例（修仙放置）**：P1 雪球式成长可见性；P2 五行克制的博弈深度；P3 零操作负担的挂机正反馈；P4 玩家间经济的稀缺感。

---

## §3 三层核心循环（Moment / Session / Long-term）

`design-strategist` 必须**分别定义三层**，工程会逐一集成——只写一层 = GDD 不完整（design-principles §一.1 的 30 秒测试只是 moment 层，session / long-term 常被漏写）。

| 层级 | 时长 | 必须回答 | 模板 |
|------|------|----------|------|
| **moment-to-moment** | 0–30s | 玩家此刻在做什么决策、为什么做 | 动作 → 反馈 → 奖励 |
| **session loop** | 5–30min | 一局的目标 → 张力 → 结果 | 目标 → 挑战 → 回报 → 再目标 |
| **long-term** | hours–weeks | 进阶钩子 + 保留动机 | 里程碑 → 新系统解锁 → 社交循环 |

- 每层都要回 Fun Hypothesis。
- **范例（RPG/ARPG）**：moment = 普攻 / 闪避手感；session = 清图 → 掉装 → 强化 → 打 Boss；long-term = 境界突破 → 新地图 → 拍卖行财富积累。

## §4 机制活检 Mechanic Biopsy

跨品类拆机制，剥掉类型外壳找内核，再重组，避免"别人有所以我也要有"。

- **步骤**：① 列出想用的机制 → ② 问 *"它真正起作用的内核是什么？"*（如"暴击"内核 = 低概率高方差的惊喜）→ ③ 能否换外壳复用（把"掉落暴击"改成"谈判暴击"）。
- **用途**：确保每个机制服务 Fun Hypothesis，而非凑功能。
- **范例**：放置游戏的"离线收益"内核 = **把时间转换为确定性的成长承诺**，不是"挂机"这个外壳本身。

## §5 经济系统：Sources & Sinks 账本（通胀第一防线）

> 🔴 **铁律**：任何一个 source 找不到对应 sink，通胀只是时间问题。GDD **必须画一张账本**，这是 idle / RPG 崩盘的头号原因，Gate 2 必查。

**账本模板**：

| 资源 | Source（产出） | Sink（消耗） | 净流向 | 风险 |
|------|----------------|--------------|--------|------|
| 金币 | 击杀掉落、任务、拍卖行卖出 | 拍卖税 5%、强化消耗、商店、修理 | `[PLACEHOLDER]` | source≫sink → 通胀 |
| 强化石 | 副本、活动 | 装备强化 | `[PLACEHOLDER]` | 单一 source 易枯竭 → 加活动 |

**量化手感（[PLACEHOLDER]，待 playtest 校准）**：
- 金币：单局（20min）产出 `≈1200`、sink `≈1100`，留 ~100 缓冲防局部通胀。*(假设平均单局 20min；若实测 35min，整条进阶与产出曲线要重画。)*
- 拍卖税 5% 是**永久 sink**，但若玩家间交易占比 <30%，它压不住总产出 → 必须补"装备销毁 / 升华"类 sink。

**检查清单**：① 每种资源都有 sink ② 顶级资源（神话装）有销毁或贬值通道 ③ 免费玩家与付费玩家都有够花路径 ④ 无无限复利 source。

## §6 数值 Tuning 纪律

- **规则 1（rationale）**：每个数值必须有"为什么是这个数"的理由，**禁止 magic number**。写不出 → 标 `[PLACEHOLDER]`。
- **规则 2（曲线优先）**：成长曲线先定类型再填数 —— 指数（`atk × 1.15^level`）用于长线滚雪球；多项式用于可控中段；线性用于保底。
- **规则 3（DPS 工作表）**：战斗类必须给 DPS 推导，确保 Boss 在 `[PLACEHOLDER]` 秒内可击杀、玩家在 `[PLACEHOLDER]` 秒内可死。
  - 沿用 gdd-template 的 Damage 公式，附加：`DPS = (Damage × 命中率) / (攻击间隔 + 前摇)`。
- **规则 4（[PLACEHOLDER] 三类标注）**：有 rationale / `[PLACEHOLDER]` / 待验证。所有**未经 playtest** 的数值标 `[PLACEHOLDER·附假设与验证路径]`。
- **规则 5（防堆叠爆炸）**：百分比加成用**加法叠加**（AtkPct 求和）而非连乘，避免 100 个 10% 变 1e10。
- **范例（RPG）**：Lv1→Lv50 atk 走指数 `base × 1.12^lv`，Boss HP 与之同阶，确保"数值成长可见"pillar 成立。

## §7 反馈通道与 Juice 规格

每个机制要定义 *"玩家该感受到什么"* + *"哪个通道送达"*。H5 游戏手感 70% 来自 juice，不在机制本身。

| 机制 | 期望感受 | 通道(视觉/音频/触觉/UI) | Juice 示例 |
|------|----------|--------------------------|------------|
| 暴击 | 爽、意外之喜 | 视觉 + 音频 | 红字放大 + 顿帧(hitstop 60ms) + 音效 |
| 升级 | 我变强了 | UI + 音频 | 光柱 + 等级数字弹跳 + 琶音 |
| 破防 | 控制感 | 视觉 | 进度条碎裂 + 屏震 |

- **规则**：每个核心动作至少一条 juice；**无通道定义的机制 = 反馈缺失风险**，集成前补。

## §8 系统交互矩阵

每对关键系统标注三者之一：**intended**（设计内）/ **acceptable**（可接受副作用，监控）/ **bug**（必须修）。提前暴露系统打架，Gate 4 集成前回顾。

| 系统 A | 系统 B | 交互 | 类型 |
|--------|--------|------|------|
| 拍卖行 | 经济 | 5% 税回收金币 | intended |
| 拍卖行 | 职业平衡 | 某职业装最贵 → 该职业泛滥 | acceptable（监控） |
| 强化 | 经济 | 强化消耗金币 | intended |
| 强化 | 拍卖行 | 强化失败装备流入拍卖 | acceptable |

---

## §9 Playtest 失败信号（bad-by 定义）

playtest 前先定义 *"坏长什么样"*，否则等于没测。每个核心系统写 A/B/C 失败信号：

| 系统 | A 失败(重画) | B 失败(调参) | C 失败(砍功能) |
|------|--------------|--------------|----------------|
| 核心循环 | 30s 内不知干啥 | 循环重复感强 | 保留但弱化 |
| 经济 | 第 3 天金币通胀 10x | 某资源局部通胀 | 加 sink |
| 数值 | Boss 0 击杀 / 玩家 0 死亡 | 战斗 >5min 拖沓 | 重做曲线 |

- **规则**：没有失败定义的 playtest 不准开。

## 与 grill-me / GDD 的对接

- **grill-me**：Step 0 逼出 Fun Hypothesis + Pillars；访谈完成见 Exit Criteria（见 `grill-me-framework.md`）。
- **GDD 模板**：新增对应小节（Fun Hypothesis / 三层循环 / 账本 / Tuning 附录 / 交互矩阵 / 失败信号），见 `gdd-template.md`。
- **Gate 2 质量门**：Fun Hypothesis 存在 + Pillars 3–5 条 + 三层循环已写 + Sources/Sinks 平衡 + 关键数值有 rationale 或 `[PLACEHOLDER]`。
